# Antigravity Prompt — Nearby Vehicle Hire Marketplace MVP

Build a realistic, mobile-first Flutter application and a separate Node.js Express REST API for a nearby vehicle hire and rental marketplace.

The application is not a taxi-booking or ride-hailing system like Uber or PickMe. It does not calculate fares, assign drivers automatically, process rides, or track vehicles in real time.

Its purpose is to help customers discover nearby vehicles, vehicle owners, and drivers. After finding a suitable listing, the customer contacts the provider directly and discusses pricing, pickup, destination, timing, and other conditions outside the platform.

For the MVP, do not integrate Google Maps or any visual map interface.

Use GPS latitude and longitude only to:

* Detect the customer’s approximate current location.
* Save a provider’s service location.
* Calculate distance between the customer and vehicle listing.
* Sort listings from nearest to farthest.
* Filter listings within a selected distance radius.

# 3. MVP User Roles

A single account may have one or more roles.

## Customer

A customer can:

* Detect their current location.
* Browse nearby vehicle listings.
* Search and filter listings.
* View listing information.
* View provider information.
* Call the provider.
* Open WhatsApp to contact the provider.
* Save listings as favourites.
* Report suspicious listings.

## Vehicle Owner

A vehicle owner can:

* Create vehicle listings.
* Add up to two vehicle photos.
* Enter vehicle information.
* Enter hire or rental availability.
* Set a service location using GPS.
* Add a contact number and WhatsApp number.
* Edit, pause, activate, or delete listings.
* View simple listing statistics.

## Driver

A driver may create a service listing without owning a vehicle.

Examples:

* Driver available for customer-owned vehicles.
* Emergency driver.
* Long-distance driver.
* Delivery driver.
* Tourist driver.
* Heavy vehicle driver.

Driver listings should be handled as a provider listing type rather than requiring a separate application.

## Hirer / Renter

Avoid creating confusing independent authentication systems for “hirer” and “renter.”

Instead, model the platform using:

```text
account roles:
- customer
- provider
- admin
```

A provider listing can have one of these types:

```text
- vehicle_with_driver
- vehicle_without_driver
- driver_only
```

This provides the intended driver, hirer, renter, customer behaviour without creating an unnecessarily complex role system.

# 4. Main MVP User Flow

## Customer flow

1. Open application.
2. View onboarding screens.
3. Allow location permission.
4. Application obtains latitude and longitude.
5. Backend returns active listings ordered by distance.
6. Customer filters results by:

   * Vehicle category
   * Listing type
   * Maximum distance
   * Availability
   * Passenger capacity
7. Customer opens a listing.
8. Customer views:

   * Vehicle photos
   * Vehicle details
   * Approximate distance
   * Provider name
   * Provider verification status
   * Phone number
   * WhatsApp contact
9. Customer contacts provider directly.
10. Customer may save or report the listing.

No booking workflow is required for the MVP.

## Provider flow

1. Register or sign in.
2. Select “Become a Provider.”
3. Complete provider profile.
4. Add a vehicle or driver service listing.
5. Capture the service location from the phone’s GPS.
6. Upload a maximum of two images.
7. Submit the listing.
8. Listing becomes:

   * pending review, or
   * active immediately, based on an environment setting.
9. Provider can manage listings from the dashboard.

# 9. Nearby Distance Calculation

Calculate distance primarily on the backend.

The Flutter app sends:

```json
{
  "latitude": 6.9271,
  "longitude": 79.8612,
  "radiusKm": 25
}
```

Use the Haversine formula in the API.

Example SQL concept:

```sql
6371 * ACOS(
    COS(RADIANS(?))
    * COS(RADIANS(latitude))
    * COS(RADIANS(longitude) - RADIANS(?))
    + SIN(RADIANS(?))
    * SIN(RADIANS(latitude))
)
```

Return the calculated value as:

```json
{
  "distanceKm": 2.45
}
```

Round display values in Flutter:

```text
Less than 1 km:
850 m away

1 km or more:
2.5 km away
```

Default nearby search radius:

```text
25 km
```

Selectable radius values:

```text
5 km
10 km
25 km
50 km
100 km
Any distance
```

Before running the expensive distance calculation, use a latitude and longitude bounding box to reduce candidate rows.

Create indexes on:

```text
latitude
longitude
status
vehicle_category_id
listing_type
available_now
created_at
```

For a later version, spatial indexes may be introduced, but do not make them a requirement for the MVP.

# 12. API Response Format

Use a consistent format.

Successful response:

```json
{
  "success": true,
  "message": "Nearby listings loaded successfully.",
  "data": [],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 42,
    "totalPages": 3
  }
}
```

Error response:

```json
{
  "success": false,
  "message": "Validation failed.",
  "errors": [
    {
      "field": "latitude",
      "message": "Latitude is required."
    }
  ],
  "code": "VALIDATION_ERROR"
}
```

Never return:

* Password hashes
* Refresh tokens
* Google tokens
* Exact identity data
* Internal database credentials
* Raw SQL errors
* Full registration numbers
* Exact provider coordinates in public listing responses

# 19. Authentication

Support:

* Email and password registration.
* Email and password login.
* Google Sign-In.
* JWT access and refresh tokens.

Access token:

```text
15 minutes
```

Refresh token:

```text
30 days
```

Store mobile tokens using Flutter Secure Storage.

Use a Dio interceptor to:

1. Attach the access token.
2. Detect an unauthorized response.
3. Attempt token refresh once.
4. Retry the original request.
5. Log the user out if refreshing fails.

Never log access tokens or passwords.

* File-extension verification.

* Soft deletion.

# 22. Offline and Poor-Network Behaviour

This is not a fully offline application, but handle unstable connections gracefully.

Flutter should:

* Cache the most recently loaded categories.
* Cache the most recent nearby listing response temporarily.
* Display cached results with an “Offline results” notice.
* Preserve partially completed listing forms locally.
* Retry failed safe GET requests.
* Never automatically retry listing creation if duplicate submission is possible.
* Show upload progress for images.
* Allow cancelled uploads.

Do not build full database synchronization for this MVP.

# 23. Performance Requirements

Flutter:

* Use paginated listing loading.
* Avoid rebuilding full screens unnecessarily.
* Use compressed thumbnails in listing cards.
* Lazy-load full-size images.
* Debounce search input.
* Cache category results.
* Use const widgets where possible.
* Display skeleton loaders.
* Avoid requesting GPS repeatedly.

Backend:

* Use MariaDB connection pooling.
* Use selected columns instead of `SELECT *`.
* Paginate every list endpoint.
* Set maximum page size to 50.
* Index common filters.
* Use bounding-box filtering before Haversine calculations.
* Generate thumbnails during upload.
* Avoid returning exact coordinates publicly.
* Use compression middleware.
* Add graceful shutdown for database connections.

# 30. Acceptance Criteria

The MVP is complete when:

1. A user can register and log in.
2. A user can allow GPS access.
3. A user can browse active nearby listings ordered by distance.
4. A user can filter listings by category, distance, listing type, and availability.
5. A user can open a listing and see its details.
6. A user can call or WhatsApp a provider.
7. A user can favourite and unfavourite listings.
8. A user can report a listing.
9. A user can become a provider.
10. A provider can create a vehicle or driver-only listing.
11. A provider can upload no more than two images.
12. The backend compresses uploaded images.
13. A provider can edit, pause, reactivate, and delete a listing.
14. A provider can see views and contact-click counts.
15. Public API responses do not reveal exact provider GPS coordinates.
16. Nearby distance is calculated by the backend.
17. The app works without any map integration.
18. The backend can be deployed as a normal Node.js Express application with MariaDB.
19. Authentication tokens are stored securely.
20. Suspended users cannot publish or activate listings.

Generate functional, connected code rather than UI-only mockups. Start with the backend database and authentication foundation, then implement the Flutter application against the real API.
